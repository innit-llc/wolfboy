## What the rule says to do, in full

Take the three groups separately, because they fail for different reasons
and the repairs are not
the same.
For a sweep that selects by an inequality, first read what the insert path
writes into the column.
Where a record can be created with no expiry, decide deliberately what
should happen to it: give
the column a real default so the sweep reaches it, or add the null case to
the sweep's own
predicate, or state in the retention record that records of that kind are
kept indefinitely and
why. Leaving the three-valued behaviour of SQL to decide it is the one
option that is not a
decision.
For a clearing call bound to one store, enumerate the stores and clear each
of them by name. Where
a library distinguishes a default instance from named ones, the top-level
call is not a shortcut
for all of them, and the code should say which instances it is clearing
rather than relying on a
reader to know the library's contract.
For a removal written as a flag, decide what the flag is for. A tombstone
that exists so other
devices can converge is a legitimate mechanism; what it is not is an
erasure, and something has to
remove the object it points at, on a schedule, with a period. Write that
period down.
For a guard that survives only as commented-out code, do one of two things
and do not leave it in
the third state: restore the check, or remove the setting it was there to
honour along with
whatever the interface says about it. A switch a person can set that no
code reads is worse than no
switch, because it tells them something about the processing that is not
so.
In every case record the outcome in the record of processing activities
against the store that
keeps the residue, with its own period and its own purpose, rather than
folding it into the period
of the store the control does reach.
