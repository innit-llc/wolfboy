## What the rule says to do, in full

Read the matched line first and decide what it is, because this rule
matches a construct that
reaches a tree in eight shapes and five of them are a disclosure: a
configuration key read at run
time, a client or request built from such a value, a schema field that
stores one per tenant, a
destination the code holds itself - an absolute URL or a bare host literal
in a
destination-naming position, or a request path appended to a
destination-named symbol, which is
the fourth construct added on 2026-08-28 as clauses 15 to 22 - and a
destination, or something
handed to one, that is assembled at run time out of a value a person saved
or a preference this
product stored, which is the fifth construct added on 2026-09-04 as clauses
23 to 30.
A sample or documentation file recording that the knob exists, an SDK's own
internals, and an
interface label are the other three, and none of them puts data anywhere by
itself.
If it is one of the five, the fix is a question and then a record row, in
that order.
Ask whoever deployed this product which object store it writes to, which
webhook endpoints its
customers have registered, and which CDN serves its assets. Those answers
are not in the
repository and cannot be put there: the same source line has a different
recipient in every
deployment. Then settle which record the category belongs in, because the
two are different
records with different fields. Where the scanned product is a CONTROLLER,
the category goes in
field (d) of its own Art. 30(1) record. Where it is a PROCESSOR - which is
the ordinary shape of a
multi-tenant product whose customers register their own webhook endpoints -
its own record is the
Art. 30(2) record, which has NO categories-of-recipients field at all: its
(d) is the
security-measures field, so writing a recipient there writes it in the
wrong place. The RECIPIENT
CATEGORY then belongs in the customer-controller's record. The product's
own record still carries
an entry about this destination whenever the destination sits in a third
country: Art. 30(2)(c) is
the processor's own transfer field and requires the third country or
international organisation to
be identified. The safeguards limb of Art. 30(2)(c) is conditional: it
requires the documentation
of suitable safeguards only "in the case of transfers referred to in the
second subparagraph of
Article 49(1)", the compelling-legitimate-interests derogation, so do not
ask for that
documentation on a transfer resting on an adequacy decision or on standard
contractual clauses.
Beside that entry, what the product owes on
its own account is Art. 28(2)'s authorisation and change-notification and
Art. 28(4)'s flow-down.
If the product's own position in the chain is not established, say so
rather than choosing one.
Write the category from what the destination receives rather than from a
product name - an object
store receives the object bytes and the object key, which usually embeds a
user or tenant
identifier; a webhook receiver receives the event payload, which is the
personal data the event is
about where the event concerns a person and is nothing of the kind where it
is a deploy or an
uptime notification; a CDN receives every visitor's IP address, user agent
and the URL of each
asset requested.
Where the set of recipients cannot be listed because the customers choose
it, write the category
by its rule rather than by its members - "the operator of any endpoint a
customer administrator
has registered on this product" is a category in the ordinary sense of Art.
30(1)(d), and it is
honest in a way that an empty field is not. Record beside it the controls
that bound the set:
whether the destination is validated before the request, and whether that
validation can be
switched off.
Then settle the two things the category does not settle. Whoever runs the
destination is usually a
processor, which needs an Art. 28(3) contract - and a contract cannot exist
with a party nobody
has identified. And where the destination turns out to sit outside the EEA,
Chapter V is a
separate question and the transfer has a separate record field of its own -
Art. 30(1)(e) where
the product keeps a controller's Art. 30(1) record, Art. 30(2)(c) where it
keeps a processor's
Art. 30(2) record.
Do not remove the configuration knob in order to close the finding. The
obligation is to record
the recipient, not to have no recipients, and a hard-coded destination is a
worse answer than a
configurable one.

WHERE THE MATCH IS THE FOURTH CONSTRUCT - a destination written into the
source itself - the first
three paragraphs still apply, with two differences. The party is NAMEABLE,
because the host is in
the code, so the record can carry a name and not only a category; and the
operator question
becomes narrower, since what is unknown is not who the destination is but
what is sent there and
in which deployments the call runs. Answer it by reading the request rather
than the host name.
Write the record row from what travels: a media-metadata lookup that sends
a title and an
identifier is a different row from an installation report that sends a site
name, a server
software string and an active-user count, and the second is the one a
reader will not expect to
find. Where the destination is reached only to fetch something - a database
download, a package
index, an upstream version check that sends nothing about a person - say so
and close the row;
a recipient of no personal data is not a recipient for field (d). Where the
request DOES carry
personal data, three further things belong beside the row: whether the call
can be switched off,
whether the destination is configurable, and whether the request travels
over TLS. And do not
answer this finding by deleting the host from the source into a
configuration value: that moves
the same disclosure into the first construct and out of the record's reach.

WHERE THE MATCH IS THE FIFTH CONSTRUCT - a destination, or something handed
to one, decided at run
time from a value a person saved or a preference this product stored - the
record is written from
the SUBSTITUTED VALUE rather than from the host, because the host is often
the only half that is
visible and it is the wrong half. Name what is put into the template or the
argument and who ends
up holding it: the address a person bookmarked, the domain of a page they
saved, a key derived
from their email, the whole configuration they built. Then write the
category by its rule, exactly
as the tenant-webhook case above does - "the operator of any site a user
asks this product to
fetch or to archive" is a category in the ordinary sense of Art. 30(1)(d)
and is the honest answer
where the members cannot be listed. FOUR THINGS BELONG BESIDE THAT ROW AND
ONLY THE FIRST IS
ORDINARY. Whether the feature is on by default or a person has to turn it
on, because a per-person
toggle is the difference between a disclosure everybody makes and one
nobody has made yet. Whether
the substituted value is disclosed to a party that is not acting for this
operator - a public
archive and the operator of a bookmarked site are recipients and are not
processors, so there is
no Art. 28(3) contract to obtain and the record says so rather than leaving
the field open.
Whether anything the product sends can be RETRACTED: where the third party
takes and publishes its
own copy, deleting the local row does not reach it, and the honest record
says the copy is outside
the operator's control - that is Art. 5(1)(e) rather than Art. 30, it is a
separate finding, and
this rule has not looked for it. And where the destination is read out of a
person's own
preference, the record cannot name a party at all: what it can state is the
rule that selects one
and the default the product ships. Do not close any of these by hard-coding
the destination or by
removing the person's ability to choose it - the obligation is to record
the recipient, and a
narrower feature is not a better record.
