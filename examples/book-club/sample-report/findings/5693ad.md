## What the rule says to do, in full

Read this only after context question 4 has been answered. This candidate
is raised by the
presence of personal data, not by the absence of a route: a project that
already ships a
self-service erasure path and a JSON export produces exactly the same
candidate as one that ships
nothing, and the difference between them is a question for the reader
rather than for the scanner.
If the routes are already there, the useful output is the note recording
where they live.
Settle the role first, because GDPR Arts. 15-22 are owed by the controller
(Art. 4(7)) and not by
a processor. A product with its own accounts is the controller for those
accounts; a service that
only handles a customer's data on that customer's instructions is a
processor for it, and owes the
narrower Art. 28(3)(e) duty to assist the controller instead. If the
repository is a processor for
everything in the locations list, record that and the candidate closes.
For a controller, the size of the team changes nothing: Chapter III carries
no micro or small
enterprise carve-out, and Art. 83(5)(b) puts an infringement of Arts. 12-22
in the higher fining
tier.
Engineering changes that close the gap, in the order they pay off:
1. An erasure path the person can start themselves, which removes the data
   rather than marking
   them. Art. 17(1) says erase. If a two-stage design is wanted - mark now,
   remove later - ship
   the second stage as a scheduled job in the same change, with the
   interval written down, so the
   mark is a queue entry and not the whole feature.
2. Propagation, which is the half that is usually missing. Art. 19 requires
   the erasure to be
   communicated to every recipient the data were disclosed to. Enumerate
   the recipients once
   (analytics, error reporting, session replay, CRM, transactional email
   and SMS, payments,
   support desk, warehouse, search index, backups and read replicas), then
   make the erasure path
   call each one's own deletion API and record the outcome. Several of them
   have one: a suppression
   or delete endpoint on the analytics vendor, a contact-delete on the CRM,
   a customer-delete on
   the payment processor. Where a store cannot be reached in-line - a
   backup, an immutable log -
   write down the retention period after which the copy disappears.
3. A copy of the data, in a commonly used electronic form (Art. 15(3)) and,
   for the data the
   person provided under consent or contract, in a structured, commonly
   used and machine-readable
   format that another controller can ingest (Art. 20(1)). A JSON or CSV
   bundle generated on
   request satisfies both; a screenshot or a PDF of a settings page does
   not satisfy Art. 20.
4. A route for the rest of Chapter III - access (15), rectification (16),
   restriction (18),
   objection (21) and a decision made solely by automated means (22) - even
   if it is one form
   that opens a ticket. Persist the request with its receipt timestamp so
   the Art. 12(3) one-month
   clock is measurable, and so an extension can be notified with reasons
   inside that first month.
5. Where a request is refused, Art. 12(4) is what the response has to
   carry: the reasons, the
   possibility of lodging a complaint with a supervisory authority, and the
   possibility of a
   judicial remedy. A handler that returns a bare 403, a 501 or "not
   available" meets none of
   that, and Art. 12(5) puts the burden of showing a request excessive on
   the controller.
6. Name the routes the way the ecosystem names them, so the next reader
   finds them in one search:
   delete_account / deleteAccount / accountDeletion for the Art. 17 action,
   delete_user_data or
   erase_personal_data for the contents, export_user_data /
   download_your_data / data_portability
   for the Art. 15(3) copy and the Art. 20(1) export, and dsar /
   data_subject_request /
   erasure_request for the intake route, with the request itself persisted
   as
   data_subject_requests. This is naming, not compliance - the scanner no
   longer reads these names
   and no longer suppresses anything on the strength of one - but a route
   nobody can find is a
   route the next audit will not credit either.
One thing that does not count as erasure: pseudonymisation. Art. 4(5)
defines it as processing
after which the data "can no longer be attributed to a specific data
subject without the use of
additional information", and Recital 26 says such data "should be
considered to be information on
an identifiable natural person" - so a pseudonymiser leaves the data inside
the Regulation and
leaves Art. 17 unanswered. Anonymisation is different: Recital 26 puts data
"rendered anonymous in
such a manner that the data subject is not or no longer identifiable"
outside the Regulation, which
is why an anonymiser that genuinely severs re-identification can discharge
the erasure duty.
Where a mechanism already exists but the scanner could not see it - a form
in a separate front-end
repository, an identity provider's own console, a documented manual
process - record where it lives
so that the next reader can close the candidate from the note rather than
re-deriving it.
