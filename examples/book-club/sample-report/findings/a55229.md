# F2 · New members' e-mail addresses and plain-text passwords are written to the server log at sign-up.
- To fix · high · Password or key written to a log or console · a55229 ·
  review of 19 Nov 2026 · [report](../report.md)
- Place: [`src/signup.ts:10`][1] ·
  `console.log("new signup", { name, email, password });`
- Provision: GDPR Art. 5(1)(f) and Art. 32 · United States, FTC Act Sec. 5
  (offered in the EU, as you said; Federal Trade Commission Act (FTC Act):
  you answered No for the US, and that alone does not decide it)
- Reason: password, e-mail and name from the request body are passed as an
  argument of console\.log, with no masking and no development-only guard.
- What to do (the AI review's suggestion; check it before applying): Remove
  the password from the log call; log no credentials.
- In general: Drop the secret from the log call or log a masked form, and
  set up redaction in the shared logger where one is used.

## What the review found

- Why it matters: New members' e-mail addresses and plain-text passwords
  are written to the server log at sign-up.
  - Data involved: passwords or keys and names or contact details.
  - Whose data: people with an account.
  - When it runs: on the shipped defaults.
  - In the shipped product: yes.
  - Law: GDPR Art. 5(1)(f) and Art. 32 (integrity and confidentiality;
    security of processing) (a duty in the higher fine tier, set by GDPR
    Art 83(5)(a)).

<details>
<summary>The review's reasoning, in full</summary>

- What the review said: The sign-up handler writes the new member's name,
  e-mail and plain-text password to the server's console log. Which clause
  fired: the console-call kind, and the password sits inside console\.log's
  own object argument at src/signup\.ts:10. The value is not masked
  upstream: src/signup\.ts:9 takes it straight from the request body, and
  it is hashed with bcrypt only afterwards (line 16), so the log carries
  the real password. Nothing guards the line in development only: it is
  unconditional, and the Dockerfile sets NODE_ENV\=production
  (Dockerfile:10 per the orientation paragraph) and copies src into the
  image (Dockerfile:6). I did not find, and did not search for, a
  log-forwarding setup (Sentry, Datadog or similar) in this repository, so
  whether the line is persisted off-host depends on how the operator
  collects container output. The fixed-sample exception does not apply
  because the value comes from a live request. The settled premise says the
  EU reaches this rule, and the code does not change that.

</details>
