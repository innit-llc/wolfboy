## What the rule says to do, in full

Read the matched line first and decide what it is, because this rule
matches a spelling a vendor
owns and that spelling reaches a tree in nine shapes of which three put
data in the vendor's
hands. A dependency declaration or import that first-party code calls; a
request to the vendor's
API or a script, tag, pixel or image loaded from the vendor's host on the
product's own request
path; and a vendor's own installation snippet in a page template are the
three. A vendored SDK
nothing calls, a documentation or migration-guide link, a
Content-Security-Policy or
cookie-declaration entry that names a host without loading it, test or demo
data, and a string
that is not the vendor at all are the other five. A supporting line of a
first-party integration
whose send exists in the tree - a setup-screen entry, a kind list, a
renderer for the vendor's
message format, a setting that selects the vendor - is the ninth: it sends
nothing itself, and it
names the recipient of the send it serves. The policy or cookie-declaration
entry transmits
nothing to the vendor by itself, and it is not nothing as evidence either:
someone wrote that host
down because they expected it to be reached, so look for the tag, pixel or
image that does the
loading before closing the candidate on the entry.
Then settle two things the code alone does not answer, in this order,
because either one can close
the candidate outright. First, IS THE TREE THE VENDOR? Two of these vendors
publish their own
source under their own name, and a product naming itself is not a
disclosure to a recipient.
Second, IS THE DESTINATION THE VENDOR'S OWN HOST, or a self-hosted instance
the operator runs?
Ten of these vendors offer an edition the operator runs itself - PostHog,
Plausible, Matomo,
Sentry, OpenReplay, LogRocket, BugSnag, Retraced, DiceBear and wsrv.nl -
and for those the package
name, the import and the call are identical either way; the difference is a
configuration value,
very often an environment variable.
An address on the operator's own domain is not evidence of self-hosting:
PostHog, Plausible, Sentry,
Mixpanel and Datadog each document such an address as a reverse proxy that
passes the data on to them.
Only where the person running the scan says it is their own instance, the
vendor is one of those
ten, and nothing in the configuration contradicts that, is there no named
recipient to record here;
for any other vendor an address on the operator's own domain is a proxy to
that vendor.
If it survives both, write the entry, and write four things into it. WHO
the recipient is, named as
it identifies itself in its own contracting document rather than by the
brand on the package - two
of these vendors trade under a name that is not their owner's. WHAT it
receives on the integration
path actually used, read off the vendor's own API reference for the call
this code makes: a
page-view beacon, an identify call, a session recording, a heatmap, a
server-side event, an avatar
image request and an audit-log event are seven materially different
disclosures that one row
should not flatten, and the request properties belong in the row beside the
payload - the caller's
IP address, the user agent, the page URL and the referrer travel on every
request whatever the
payload is, and the page URL routinely carries an order number, a document
title or a token. For
an avatar host record what the request key IS: a hash of a person's email
address is an identifier
and not an anonymisation, and a name in a query string is the name itself.
WHICH ENTITY the operator
actually contracts with and WHERE that entity is, as a place, read from the
order form or the data
processing agreement rather than the vendor's homepage - and THE VENDOR HAS
NO SINGLE ANSWER TO
COPY, because a vendor of this kind names several entities and picks
between them by a property of
the CUSTOMER, so the entity is a fact about THIS OPERATOR'S CONTRACT.
Context question 6 lists the
candidates each vendor's own documents named and the date each was read;
that is an incomplete list
of candidates and never the answer, because nothing re-reads those
documents. Where the operator
cannot produce the contract, return needs_human for that field rather than
choosing the candidate
that looks likeliest. And WHETHER it is a processor or an independent
controller for this data.
For the vendors the context questions name as having no established
jurisdiction - Hotjar
(Contentsquare), Microsoft Clarity, the wsrv.nl image proxy, UI Avatars and
Retraced - leave that
field unanswered and say why. Do not substitute a headquarters, a billing
country or a country
inferred from a domain suffix.
Which record the entry goes in depends on whether the scanned product is a
controller or a
processor for this data, and there is no field to write it into until that
is answered. Where the
product is a controller, the entry is a category of recipient in field (d)
of its own Art. 30(1)
record. Where the product is a processor, its own record is the Art. 30(2)
record, which has no
categories-of-recipients field - its (d) is the security-measures field, so
the words FIELD (D)
name something else entirely there, and the recipient category belongs in
the customer-controller's
record instead. If the product's own position in the chain is not
established, say so and stop
rather than choosing one.
In either case add the vendor to the privacy policy, the cookie declaration
and the published
subprocessor list as well as to the record, because for this class those
are the documents that
most often lack it - an analytics tag and an avatar host arrive as one line
of template code and
nobody experiences either as engaging a third party.
If the vendor is already named in the record, in the privacy policy and in
the subprocessor list,
and the four facts above are recorded, dismiss the candidate and say
which of the three documents you read. Check as well whether the same
vendor already appears in
this output under a separate rule about prior consent for tag placement;
the emitter does not
de-duplicate across rules, and two duties about one vendor is not one
finding reported twice.
Do not delete the analytics tag, the avatar image or the audit log in order
to close the finding.
The obligation is to record the recipient, not to have no recipients - and
for an audit log the
obligation to keep it may come from somewhere else entirely.
