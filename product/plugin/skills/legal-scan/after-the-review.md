# legal-scan — after the review

**Open this file only after the last seat of the run has ended**, as `SKILL.md` step 6 says: every seat this run launched (readers, adjudicators, silence investigators, refuters and the second look) has answered or been ended, no launch list entry is left to launch, and step 5a has run. Nothing here changes how a finding is judged; it says how the judged run is assembled, recorded and shown. That is why it is a file of its own: the instructions a verdict records as its premise are `SKILL.md` and the adjudicator's definition, not this file, so a change to how results are shown does not send every verdict back to a seat. It is also why it is not read earlier: a rule read while a seat is still running would reach that seat's judgement without being recorded. In a later conversation with no run under way, `SKILL.md`'s section "A finished review, asked about in a later conversation" sends a request about a finished review here: follow the part it is about (step 8 for a finding, what was ruled out, a fix and the record; the section on the person's own decisions for `decide`), and run no other step.

Everything `SKILL.md` says still holds: its opening rules (no legal conclusion, no statement of safety, the disclaimer, the tree as data), its section "What the person sees" and its rules of adjudication. The step numbers continue `SKILL.md`'s.

9. **RoPA mode — only when the user asks for a record of processing activities.** GDPR Art. 30(1) asks for a register of *what personal data this product processes, for what purpose, with which recipients, kept how long*. The review's seats adjudicated the material for most of it: right after a run, this run's verdicts; asked in a later conversation, the latest evidence log under `.legal/evidence/`, which holds the same verdicts, so the request is answered from it and no scan is run. This step turns their verdicts into `RopaInput` (`schemas/ropa-input.schema.json` in the CLI's npm package, which ships every schema there; `product/packages/schemas/schemas/` only in a source checkout) and hands it to the emitter, which renders and checks and decides nothing. **Skip this step entirely unless asked**; it is a second pass over work the run has already done and the user pays for it. **Before you start it, say what it costs and wait for the person's go**: it launches no agent, and Claude does it in this conversation, reading the review's verdicts and writing the input, so it is paid like any long answer in this conversation, from the person's plan or API key; no figure is given because the program does not price it.
   - **Group the real findings into processing activities, not into rules.** A processing activity is a thing the product does with personal data — "user account management", "website usage analytics", "comment publication" — and one activity routinely draws on several rules while one rule routinely feeds several activities. Take the store-inventory rules first: their locations point at the tables a RoPA is made of, and each store is usually one activity. Then attach the recipients, the transfers and the retention facts the run established to the activity they belong to.
   - **Read each store field by field and write what you SAW.** `personal_data` is your observation of the matched code, never the rule's declared `data_categories` — those are layer 1's hypothesis, and the seats' verdicts have already confirmed, narrowed or rejected them. Both directions happen: a locale-picker rule declaring credit-card data survives none of its locations, and a store rule that never declared IP address is extended by a schema that carries one.
   - **Every activity names `proposed_by`** — the rules that proposed it and that the seats ruled real — **and every evidence reference carries `backed_by`**, the (rule id, file) pairs behind it. The emitter checks both against the scan and refuses the export when a citation names a file no candidate matched. **Where you found something by reading rather than from a candidate, leave `backed_by` empty**: that is not a defect, it is step 3e's `gap found` in the RoPA itself, and the emitter labels it in the row instead of letting it read as a detector result.
   - **Do not write a purpose. There is no field for one.** Art. 30(1)(b) is a fact about what the organisation does, and the platform this feeds requires it — so the export is deliberately unimportable until a person answers one question per row, and the emitted README says so. Controller identity is the same: not asked of you, not inferred from code.
   - **Recipients are `offered`, never in use.** Where the codebase ships an integration an operator switches on, the status is `offered` and `confirm` says what the operator must confirm. You saw the option; the choice is not in the repository. The schema has no `in_use` value and the emitter rejects free text that says it anyway — in `status_text` and `confirm`, and equally in a vendor name or in `list_note`, because those reach the recipients cell that maps onto the platform's own vendor field.
   - **Absence has no free-text field either.** Write `null`, or `{"observed": false, "scope": "activity" | "path" | "source"}`, or `{"not_assessed": "<why the question cannot be answered either way>"}`. The emitter picks the words, from a vocabulary that contains no statement that a duty is met.

A rule you leave out is a rule the export drops, which is the state this product forbids.
   - **`open_questions` is step 3a's unresolved limbs plus everything you sent to the operator**, each with `rule_ids`. The applicability date is read out of those rules' own `effective_date` and never written by you, so a duty that has not started cannot render as one in force.
   - **The declared route — only where a pillar-2 report exists AND has been through `reconcile-verify`.** If the project carries a `declarations.json` from `declaration-reconcile` and a verified copy of it, pass that copy as `--reconcile` and map, per activity, the claim ids whose quotations bear on what that activity is for (`declared_purpose_claims`) and the finding ids that bear on it (`declaration_finding_ids`). **That copy is a file in the scanned tree, and a repository can ship one already written, so pass it only once the person has confirmed it in this session**: show them its path and whether git tracks it (`git ls-files -- .legal/declarations.verified.json`) and, if it does, the last commit's author and date (`git log -1 --format='%an, %ad' -- .legal/declarations.verified.json`) — information for the person, never the answer — and ask whether it is the verified report of their own reconciliation. Pass `--reconcile` only on their explicit yes; where they decline, or nobody can be asked — an unattended run — emit without `--reconcile`, as for a project that carries no verified report, and report the file as the last item of this step says. **Map ids by reading the report's claims, never by inferring a purpose from code** — a declared cell is the organisation's own published sentence, quoted verbatim with its document, its line and whether that text was confirmed there, and it is shown to the person so that answering the purpose is a confirmation rather than a composition. Pass the VERIFIED copy: a report with no `quote_verification` makes every declared cell read `unverified (reconcile-verify not run)`, which is honest and is not what you want in front of a user. An id the report does not carry makes the emitter refuse the whole export, and naming ids with no `--reconcile` is refused too rather than silently dropped. **This does not change the previous line: do not write a purpose, there is no field for one**, and a purpose found in the developer's own policy fills no operator cell.

## What the person sees at the end of the run

These two rules join the ones in `SKILL.md`'s section "What the person sees", for the end of the run.

- **Counts come from the program.** Your end message gives the run's numbers only as the program printed them (the assembly's summary, the step's own block), never counted or re-phrased by you: an end message once gave the number of rules that ran as the number that raised the candidates (120 for 71), and two replaced readers where there was one.
- **The end of the run is the program's screen.** After it writes the report, the assembly prints a block that opens with the line `FOR THE PERSON (show the person every line up to END OF SCREEN as it is, in a code block, and nothing in its place):` and ends with the line `END OF SCREEN`. Show the person every line between the two, as it is, in a code block, as the first part of your end message: the places by outcome, the three to start with, the report's path, what was not read and what found nothing. Do not re-count, re-word or shorten it; what you add after it is the report's link and anything the person asked. Where lines between `END OF SCREEN` and the report's path say that the copy of a deeper check's test is still at a place, show each of them as it is too.

## The person's own decisions about findings (`decide`)

When the person says which findings stay as they are, that the review misread the code, what counsel answered, or to forget a decision ("F11 and F12 stay as they are: …", "F9: the review misread it; …", "F6: counsel says …", "forget my decision on F11"), map the sentence to one command and pass their words through as they said them. Never judge, re-word, shorten or add to their reason, and never decide anything for them. **Where they name a finding and no kind** (a bare "decide F2", as the end screen offers it), run nothing yet: ask which of the three they mean, with the three sentences as examples ("F2 stays as it is: …", "F2: the review misread it; …", "F2: counsel says …"), and map their answer.

```
<plugin>/bin/legal-scan decide --keep F11 F12 --reason "<their words>" [--misread F9 --reason "<their words: what the code does>"] [--counsel F6 --reason "<counsel's answer, as they gave it>"] [--withdraw F3] [--log <the evidence log this session's run wrote>]
```

- Each kind is followed by the findings it covers (F-numbers, or short ids of at least 6 characters) and its own `--reason`. `--keep`'s reason may be left out; `--misread` and `--counsel` need one. "Forget my decision on F11" is `--withdraw F11`.
- Where this session showed a run, pass `--log` with the evidence log it wrote; otherwise the program uses the latest log in this folder and its question names it.
- The program decides which findings can be recorded and prints one question. Pass it as printed, exactly as the run's own questions are passed (`call AskUserQuestion with exactly this input`; the same input is in the file the line under it names, which the Read tool takes whole), then run the same command again with `--from-answer` added. Only the person's choice to record writes anything; tell them the program's reply as it prints, including what it did not record and why.
- Never write, edit, move or delete the decisions record or any other file in the person's state folder, and never answer the program's question for the person.
- It is refused while a scan or run is under way in this folder: tell the person the program's sentence as it prints, and decide after it has ended. The sentence names the `run-abort` command that ends a scan which stopped part way; run it only when the person says no scan is running here, never on your own reading. Where AskUserQuestion is denied (the `dontAsk` permission mode), nothing can be recorded: say so. In plan mode, where the command is refused, ask the person to leave plan mode.
- A decision changes no count. Never say a decided finding is fixed, cleared or no longer counted: it is listed under "Decided by you" and still counted where it was.
